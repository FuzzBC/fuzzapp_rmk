FuZz TestMode — round 2: five different UX layouts

Not palette swaps this time — five different information architectures for the same command console (same Diffuser + SmartTV command set, same simulated fake device underneath). Pick whichever navigation model fits how you'd actually use this tool during a test pass, and I'll build the real .hta on it.

UX 1 · COMMAND PALETTE
Raycast / Spotlight-style
Dashboard home with live status tiles + recent activity. ⌘K (or "/") opens a fuzzy search palette over every command; picking one slides in a right-side inspector. Log lives in its own bottom sheet.
UX 2 · DASHBOARD + SHEET
Smart-home app style
Big hero status card with primary actions right on it, category tiles below. Tapping a tile slides up a bottom sheet where each command expands inline. Activity is a separate slide-over panel.
UX 3 · WIZARD / FOCUSED CARD
Mobile-first stepper
Phone-frame layout: one big focused command card at a time, prev/next arrows step through a category, bottom tab bar (Home / Commands / Log) swaps the whole screen like a native app.
UX 4 · TILE BOARD
Control-panel grid (macOS Settings-style)
Every command is a tile in a grid, grouped by section. Click a tile and it expands full-width right in the grid with its controls — no separate panel to jump to. Slim always-on activity column on the right.
UX 5 · IDE WORKSPACE
VS Code-style
Explorer tree (folders = categories, files = commands) opens commands as tabs — several can stay open at once, each keeping its own state. Bottom panel: LOG / QUICK TEST / RAW, like Terminal/Output. Status bar at the very bottom.
Same rules as round 1: every Send here runs against a small in-memory fake device (shared/engine.js) — mode, colour, parfum timer, settings all persist and echo back — not a real socket yet. The real .hta will shell out to PowerShell for actual UDP/TCP sends, same as the old TestMode.hta in this repo's history.

What's shared vs. what's different: all five use the same param-control widgets and the same "what came back" renderer (shared/controls.js / shared/result-view.js) restyled per mockup — that's normal (every real app reuses its own input components). What's genuinely different between these five is the navigation model: palette-driven vs. dashboard-and-sheets vs. one-card-at-a-time wizard vs. an all-tiles board vs. a multi-tab IDE. That's the actual UX decision to make here.

IE11 caveat still applies: mshta.exe renders with Trident/MSHTML, not Chrome. Flatter looks (2, 4, 5, and 9's grid) carry over closely; blur/backdrop effects (none of these five lean on that as heavily as round 1's Aurora did) and CSS Grid get translated to flexbox-based layouts for the real build.
